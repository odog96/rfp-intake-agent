## 1. The problems this plan fixes

All three were found by reading the code and running the PLAN step offline on the two sample documents
(`samples/Synthetic_RFP_NEOD001.pdf` and `samples/Example protocol 2.pdf`) with the first parser,
`ingest/parsers/rung1.py`.

1. **The study phase is read from a different study.** Section 1.3.2 of the protocol, "Clinical
   Experience" (PDF page 39), describes another study, NEOD001-001, which is an ongoing, open-label
   Phase 1/2 study. The extract step returned `phase_1_2` from that passage. This is known problem 1 in
   `CLAUDE.md`. No step in the pipeline decides whether a passage is about this study or another one.
   The extraction model did write "Study NEOD001-001 (referenced prior study)" into the record's scope,
   but RECONCILE compares values only within one scope, so the two phase values were never compared
   and no disagreement was raised.

2. **PLAN depends on PDF bookmarks.** Bookmarks are the optional heading list a PDF file can carry,
   which readers show as a clickable outline. `plan/__init__.py` scores only the bookmarked sections.
   With no bookmarks, every field group gets pages 1 to 5 (`FALLBACK_PAGES = 5`). The synthetic RFP has
   0 bookmarks and 6 pages, so page 6, which lists the services the sponsor wants, was never sent to the
   extract step. The protocol has 176 bookmarks.

   Not checked: whether the second parser (`rung2.py`, Docling) ran on the RFP in the live run and
   found headings. It could not be installed in the design session.

3. **The smallest unit PLAN can send is a whole page, plus one page of margin on each side.**
   `_build_excerpt` in `extract/prompt.py` sends every word on the chosen pages. So text from a
   neighbouring section that was not chosen still reaches the model. Page 39 holds the end of section
   1.3.1 and the start of section 1.3.2, so no whole-page choice can keep one and drop the other.

A contributing cause: the `phase_population` group in `config/fields.yaml` lists the headings
"Background" and "Rationale" in its `search_hints`, which steers PLAN towards the sections where other
studies are described.

## 2. The new pipeline

Three new graph nodes go between CLASSIFY and PLAN. PLAN, EXTRACT and DERIVE change. The other nodes do
not change.

```
INGEST → CLASSIFY → FIND_SECTIONS → SET_ASIDE_SECTIONS → MARK_OTHER_STUDY
       → PLAN → EXTRACT → NORMALIZE → RECONCILE → ADJUDICATE → DERIVE → GATE
```

| Node | New or changed | Uses a model? | Job |
|---|---|---|---|
| FIND_SECTIONS | new | no | Split each document into sections with exact start and end positions in the text |
| SET_ASIDE_SECTIONS | new | no | Remove sections whose heading is on a configured list of sections Angus ignores |
| MARK_OTHER_STUDY | new | yes | Remove passages that describe a different study, and record each removal |
| PLAN | changed | no | Choose sections, not whole pages, for each field group |
| EXTRACT | changed | yes | Read only the kept text of the chosen sections |
| DERIVE | changed | no | Add the placebo-matching conclusion Angus described |

`CLAUDE.md` rule 1 still holds: every edge stays a static Python edge. The model in MARK_OTHER_STUDY
only labels text. It never decides which node runs next.

## 3. Build order

Build and test one stage at a time, in this order. Each stage must pass its own test, and the full
offline suite (`pytest`) must stay green, before the next stage starts. Commit after each stage.

### Stage 1 — FIND_SECTIONS

**What it produces.** For each document, a list of sections in document order. Each section records:
the heading text, its level, the page it starts on, and its start and end positions in the document's
text. A section ends where the next heading of any level begins. Store the list on `Document` in
`domain/schemas.py` (for example a new `sections` field), so it travels in the graph state the same way
`outline` and `page_texts` already do.

Positions must be precise enough to cut a page in two. One straightforward approach: keep `page_texts`
as it is, and record each boundary as (page number, character offset within that page's text).

**Where the boundaries come from, tried in this order:**

1. **Bookmarks**, when the PDF has them. Use each bookmark's page, then find the heading's text on that
   page to get the character offset. If the heading text cannot be found on that page, fall back to the
   start of the page and log it.
2. **The whole document as one section**, when the PDF has no bookmarks and its whole text fits inside
   PLAN's token budget (`DEFAULT_TOKEN_BUDGET = 4000`, estimated as characters divided by 4). The
   synthetic RFP is about 1,900 tokens by that estimate, so it lands here and every page, including
   page 6, is read.
3. **Headings found in the page text**, when there are no bookmarks and the document is too long for
   rule 2. Look for numbered headings ("1.3.2 Clinical Experience"), lines in capitals ending in a colon
   ("STUDY SYNOPSIS:"), and short lines in a larger or bold font (PyMuPDF's `page.get_text("dict")`
   gives font size and weight). This is a best guess and will be wrong sometimes. Keep it simple and
   log how many headings it found.

Record on each document which of the three rules produced its sections, for the report and for
debugging.

**Do not change** the parsers in `ingest/parsers/`. FIND_SECTIONS reads what INGEST already produced.

**Test (offline).**
- On `samples/Example protocol 2.pdf`: section "1.3.2 Clinical Experience" starts on page 39 and ends
  where "1.4 Rationale for Dose Selection" begins on page 40, and the boundary inside page 39 falls
  after the last sentence of section 1.3.1 ("...as would typically be performed in clinical
  development, is warranted.").
- On `samples/Synthetic_RFP_NEOD001.pdf`: one section covering pages 1 to 6, produced by rule 2.
- A unit test for rule 3 on a short hand-written text with numbered and capitalised headings.

### Stage 2 — PLAN and EXTRACT work on sections

**PLAN** (`plan/__init__.py`, `plan/scoring.py`): score sections from FIND_SECTIONS instead of bookmark
entries, using the same `search_hints` and the same scoring weights. Drop the one-page margin, because
section boundaries are now exact. Keep the top-k and token-budget splitting. Remove the
"pages 1 to 5" fallback; with FIND_SECTIONS every document has sections. A document produced by rule 2
(one section) is sent whole to every group.

`ExtractionTask` (`domain/schemas.py`) carries the chosen section ids, plus a `page_window` equal to
the first and last page those sections touch, because `extract/validate.py` checks each record's page
against `page_window`.

**EXTRACT** (`extract/prompt.py`): `_build_excerpt` builds the excerpt from the chosen sections' text
only, still tagged with "--- Page N ---" markers so the model can report a page. `build_excerpt` is
also what quote validation uses (`extract/__init__.py`, line 49), so the model and the validator keep
seeing identical text. Do not build a second excerpt function.

Tables: `TableData` has a page but no position on the page. Include a table when its page is inside a
chosen section. This can let a table from a neighbouring section through; accept that for now and note
it in `CLAUDE.md`.

**Test (offline).**
- PLAN on the two sample documents produces tasks whose text for the synthetic RFP includes page 6.
- No task for the protocol contains text from a section that PLAN did not choose.
- The existing PLAN and EXTRACT tests are updated, not deleted.

### Stage 3 — SET_ASIDE_SECTIONS

A new config file, `config/sections.yaml`, holds two lists. Matching is case-insensitive on the
section heading, ignoring the section number.

- **`set_aside`**: headings for sections Angus ignores. Take the list from
  `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 4. For example: amendment history, summary of changes,
  table of contents, glossary, abbreviations, inclusion criteria, exclusion criteria, eligibility,
  adverse event reporting, serious adverse events, pregnancy, concomitant medication, prior and
  concomitant therapy, data monitoring committee, committees, sample size, record retention, quality
  assurance, informed consent, ethics, publication, references, nonclinical, contraception,
  questionnaires.
- **`keep_if_contains`**: phrases that keep a section even when its heading is on `set_aside`, because
  Angus warned that budget information sometimes hides there. At least: "unblinded", "interim
  analysis", "schedule of activities", "schedule of events", "schedule of assessments", "case report
  form", "CRF", "monitoring visit".

Do **not** put these on `set_aside`, because Angus said to scan them: statistical considerations (for
interim analyses), drug packaging and storage (for unblinded staff), and appendices (for the schedule
of activities). See `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 5.

Setting aside a section also sets aside the sections nested under it (higher level numbers, until the
next heading at the same or a higher level).

Rule: only remove what is positively on the list. Never keep only an expected list and drop the rest.

Record every set-aside section (document, heading, pages) in the graph state. It is not shown in the
report, to keep the report short, but it goes into `extraction.json`.

This stage is skipped for an RFP produced by FIND_SECTIONS rule 2 (one section), because there is
nothing to set aside.

**Test (offline).** On the protocol, the glossary, the inclusion and exclusion criteria and the
references are set aside; "Statistical Considerations" and the study-drug storage section are kept; a
hand-built section headed "Storage" that contains "unblinded pharmacy staff" is kept.

### Stage 4 — MARK_OTHER_STUDY

The one new model call. The question it answers for each section: does this text describe the study
being budgeted, or a different study?

**Input to the model.**
- The identity of this study: the protocol number from CLASSIFY (`Document.protocol_id`) and the title.
  If the documents disagree on the protocol number, use the protocol document's value.
- A batch of sections that survived SET_ASIDE_SECTIONS, each with an id and its text. Batch sections
  into calls under the existing token budget, so a 137-page protocol takes roughly ten calls rather than
  one per section. Do not pre-filter sections with keywords; keyword matching is what failed.

**What the prompt tells the model** (from `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 8). A passage
describes a different study when it:
- describes a study that is ongoing or already completed,
- gives a different study number,
- gives a different phase or design from this study,
- reports past results or a past data cutoff.

**Output from the model, per section:** one of `this_study`, `other_study`, or `mixed`, plus a
one-sentence reason. For `mixed`, the model also returns the exact sentences that describe the other
study. Each returned sentence must be validated as a substring of the section text, in code, exactly as
EXTRACT validates quotes (`extract/validate.py`, `validate_quote`). A sentence that fails validation is
not removed, and the failure is logged.

**What happens to the text.** `other_study` sections and validated `mixed` sentences are removed from
the text PLAN and EXTRACT see. Removal means the excerpt builder leaves them out. Record each removal
in the graph state: document, section heading, pages, the removed text, and the model's reason.

**Model routing.** Add a new role, `other_study_check`, to `config/models.yaml` with the same binding as
`classify`. Add a default fixture for it in `llm/mock.py` so the offline suite runs. `privacy_mode`
stays `mixed` for testing; this plan does not change it.

**Report.** Add a short appendix to `report.pdf`, "Passages removed as describing a different study,"
listing each removal with document, section heading, pages and reason. A person must be able to see
what the tool removed and why. Build it in `render/report_model.py` and `render/pdf_renderer.py`
without changing the existing sections of the report.

**Test.**
- Offline, with the mock: a hand-built section in the style of section 1.3.2 is removed and recorded.
- Live, on Bedrock, with the two sample documents only (they are synthetic or publicly registered, so
  this is allowed under `CLAUDE.md` rule 5): run the whole pipeline. It passes when:
  - `study.phase` comes back `phase_3`, and there is no `phase_1_2` row for this study. Baseline run
    `r-20261002-200521-stage2` still has that row, flagged `needs_review` at confidence 0.8 from page
    40, so this criterion is a real change in behaviour and not already satisfied;
  - the new report appendix lists section 1.3.2 of the protocol;
  - **at least 26 of the 36 registry fields have one or more rows with status `confirmed`** — the count
    from baseline run `r-20261002-200521-stage2`. If it falls below 26, MARK_OTHER_STUDY is removing
    text it should not; stop and report.

  Count fields with a confirmed row, not rows. Rows are field × scope, so a row count moves when the
  model merges or splits scopes and says nothing about whether a field was answered. Quoting a row
  count as a field count is what made the stale "108" in `CLAUDE.md` unusable.

**The five `mixed` removals from run `r-20261002-213531-stage4`, added 2026-10-02.** That run passed all
three criteria above and still removed three sentences that describe this study. Each names outside work,
and the model read "mentions another study" as "is about another study". `other_study/prompt.py` now
carries a subject test and these sentences as worked examples. A later live run passes only when none of
the first three sentences below appears in `removed_passages` in `runs/<id>/extraction.json`:

1. **Must be kept.** PROTOCOL SYNOPSIS p.24, section 3.4.1.4.8.5 Pharmacokinetics p.46 and section 10.5
   Pharmacokinetic Analyses p.97 each carry one form of: "Serum NEOD001 concentrations from this study
   will be pooled with data from similar samples from other NEOD001 studies in a population PK analysis."
   The subject is this study's own samples, so this is this study's analysis plan and a cost item.
2. **Must be kept.** Appendix 1: Organ Response and Progression Criteria p.109, 370 characters at offsets
   1197–1567: "In addition to the progression criteria listed above, Investigators will use their best
   clinical judgment … A repeated assessment at an interval that is determined by the investigator is
   required to confirm the progression." This study's own procedure, and it carries a visit.
3. **Must be kept.** Appendix 2: Stratification Details p.110, 158 characters at offsets 456–614:
   "Modified from the value of 0.025 ng/mL cited in Kumar et al, to 0.03 ng/mL, which is the lowest
   validated determination for this commercially available test." This study's own threshold; the
   citation explains where the number came from.
4. **Harmless either way.** The bare citations in the same two appendices — "Modified from Table 2 in
   Comenzo 2012.", "Palladini 2014. Coelho 2012.", "Source: Kumar 2012.", "Source: Palladini 2014." —
   are references rather than studies. Keeping them costs a few tokens and removing them loses nothing,
   so they are not a pass criterion. The prompt lists them under keep, because one rule is easier for a
   model to follow than two.
5. **Must still go.** Section 1.3.2 Clinical Experience p.39–40, removed whole. It reports study
   NEOD001-001's design and results, so a subject test must not save it. This is criterion 2 above and
   it stays.

### Stage 5 — field registry and DERIVE

All in `config/fields.yaml` unless stated. Follow `CLAUDE.md` rule 4: no field is hardcoded in Python,
except the one DERIVE rubric entry each derived field needs (`derive/__init__.py`, `DERIVE_RUBRICS`).

1. **Search hints.** Remove "Background" and "Rationale" from the `phase_population` group's
   `search_hints.headings`. Do this after stage 4 passes, so the stage 4 test shows MARK_OTHER_STUDY
   working on its own.
2. **Indication and population.** Rewrite the `hint` of `study.indication` and `study.population` to
   state the difference: the indication is the disease the drug is meant to treat; the population is
   who takes part in this study. Use the headache example from
   `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 3.
3. **Healthy volunteers.** Add to the `hint` of `design.healthy_volunteers`: when the answer is no, the
   quote must be the phrase naming the patient population (for example "subjects with light chain (AL)
   amyloidosis").
4. **New field `study.primary_objective`** (text, group `phase_population`, source_priority protocol):
   the primary objective copied verbatim. Angus asked for it in the report as written.
5. **New field `blinding.placebo_matching`** (enum: `matching_stated`, `not_matching_stated`,
   `not_specified`; group `blinding_monitoring`, budget driver). The `hint` must say that matching means
   matching as supplied to the site, and that text saying the prepared infusion bags look identical
   does not count as matching. See `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 6, rule 5.
6. **New field `blinding.unblinded_staff_stated`** (enum: `yes`, `no`, `not_specified`; group
   `blinding_monitoring`): whether the document states that unblinded staff, such as unblinded pharmacy
   staff, are required. Read off the page only; no inference.
7. **New field `visits.schedule_present`** (enum: `yes_body`, `yes_appendix`, `no`; group `visits`):
   whether a schedule of activities exists and where. Aliases: "schedule of activities", "schedule of
   events", "schedule of assessments", "SoA", "SoE".
8. **Aliases.** Make sure `ops.sites_total` has "centers" and "centres" among its aliases.
9. **New derived field `blinding.placebo_assumption`** (derived from `blinding.design`, `ip.form`,
   `blinding.placebo_matching`, `blinding.unblinded_staff_stated`), with a rubric in `derive/` that
   applies the rules in `docs/ANALYST_PROCEDURE_PROTOCOL.md` section 6, in this order:
   - open-label → "not applicable: open-label";
   - matching stated or not matching stated → use what the document says;
   - not stated, drug injected or infused → "probably not matching; unblinded handling likely";
   - not stated, drug oral → "matching not confirmed; oral drug; do not assume unblinded monitoring".
   The rubric's explanation must name the inputs it used.
10. **Contradiction between two different fields.** When `blinding.placebo_matching` is
    `matching_stated` and `blinding.unblinded_staff_stated` is `yes`, the documents contradict
    themselves and the sponsor must be asked. **RECONCILE cannot catch this**: it compares values of
    the same field only (`reconcile/__init__.py`). Implement it inside the `blinding.placebo_assumption`
    rubric: its value says the documents contradict each other, with both quotes in the explanation.
    GATE already sends every derived field to `needs_review`.

**Test (offline).** Table-driven tests for the rubric covering all four rules and the contradiction. A
registry test that the new fields load. Live: one more Bedrock run on the sample pair, checking that
`blinding.placebo_matching` comes back `not_matching_stated` (the protocol says "a matching placebo will
not be provided") and `blinding.unblinded_staff_stated` comes back `yes`.
